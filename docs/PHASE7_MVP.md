## One-line goal

Own every executor turn and route all LLM calls through a single proxy — so Phase 8 can capture 100% with no bypass paths.

## North-star acceptance (dogfood)

After a live `delegate_to_agent` call on `mcp_coder_phase1_e2e`:

1. **Every executor LLM turn** is a `llm_call` event in `traces/<delegation_id>.jsonl` — prompt + response bodies + tokens + step index.
2. **Non-LLM actions** (file edits, shell calls, lint retries) appear as `tool_call` / `action` events in the same trace file.
3. **All owned LLM calls** (helpers + executor tap) route through `LlmGateway` — one code path, one capture boundary.
4. **Compile bundle** fields (`builder_input`, `architect_output`, `final_executor_prompt`) are present in trace or sidecar at `standard` verbosity.
5. `mcp-coder maintenance stats` reports executor turn count per delegation (not just 3 helper lines as today).

---

## Strategic context

Phase 6 shipped the observability substrate — clean seam, helper LLM trace files, live tokens via Route B (`owned_completion`). But two structural gaps remain before "100% capture" is achievable:

1. **Executor inner loop is opaque.** Aider's `coder.run(prompt)` is a black box: multi-turn LLM calls, file edits, shell executions, lint retries happen inside without producing trace events. Today the trace file for a delegation has 3 helper lines only; the executor's actual work is invisible.

2. **Two capture paths exist.** Route A (LiteLLM `success_callback`) covers the opaque executor shim. Route B (`owned_completion`) covers helpers. Both are transitional. Any new LLM call site must decide which route — this is unsustainable and cannot scale to Phase 8's write-always requirement.

Phase 7 fixes both:
- **LlmGateway** collapses Route A + Route B into one proxy. One call site, one boundary, one capture point.
- **Executor loop ownership** breaks the black box: every turn is an event, every action is an event.

These are the prerequisites Phase 8 needs before it can safely say "write 100% of everything."

## Milestones

### P7-001 — LlmGateway proxy: unified completion boundary *(BL-368)*

**Status:** `open`

**Goal:** Replace the dual-path capture (Route A callback + Route B `owned_completion`) with a single `LlmGateway` in `core/observability/`. All owned LLM calls — helpers, `test-model`, future backends — route through it. The LiteLLM callback becomes a thin shim or is removed. This is the prerequisite for P7-002 (executor turns via owned loop).

**Why first:** Until every LLM call goes through one boundary, capturing 100% is impossible — new call sites will naturally bypass whichever route they don't know about.

**Scope:**
- `core/observability/gateway.py` — `LlmGateway` class wrapping `litellm.completion`
- `ObservabilityBackend` notified synchronously after each call (tokens, trace body, reasoning)
- `NullObservabilityGateway` for tests (swap in, no I/O)
- Migrate: `core/engine/owned_helper_llm.py` → routes through gateway
- Executor path: proxy tap point even while still using Aider adapter (bridge until P7-002 owns loop)
- Broader scope than logging: tokens, trace bodies, reasoning content, future: budget caps, redaction, rate limits
- LiteLLM callback (`core/observability/litellm_callback.py`) becomes thin shim or removed once gateway covers all paths

**Acceptance:**
- All helper LLM calls (`context_builder`, `architect_pass`, `spec_validation`) go through `LlmGateway`
- `LlmGateway` produces identical `llm_call` trace events as today's `record_owned_completion`
- `NullObservability` tests pass with gateway swapped for no-op
- `test-model --via litellm` reports token counts through gateway
- Existing helper token counts + trace file tests still green
- No direct `litellm.completion` calls outside gateway (except backward-compat shim if needed for Aider)
- `core/observability/` has no imports from `server/` or `core/engine/aider_engine.py`

**Files touched:** `core/observability/gateway.py` (new), `core/observability/base.py` (gateway interface), `core/observability/null.py`, `core/engine/owned_helper_llm.py`, `tests/`

### P7-002 — Executor loop ownership: per-turn trace events *(BL-350)*

**Status:** `open`

**Goal:** Break Aider's `coder.run(prompt)` black box into an owned loop that emits a trace event for every executor LLM turn and every non-LLM action (file edit, shell call, lint retry). Preferred route: **outer loop (Route A)** — `compile → run(bounded sub-task) → inspect → recompile → run`; Aider `Coder` subclass (Route C) only if Route A is insufficient for per-turn capture.

**Depends on:** P7-001 (LlmGateway must exist before executor turns can be recorded through it)

**Scope:**
- Per-turn `llm_call` events in `traces/<delegation_id>.jsonl` — same format as helper events, plus `step_index` and `parent_call_id`
- Non-LLM action events: `tool_call` (file write, shell exec) and `action` (lint retry, confirm, other executor actions)
- Turn sequence reconstructable from trace file alone (step_index monotonic per delegation)
- Reasoning tokens per executor turn when model emits (extends P6-004 capture; BL-333)
- Step budget + timeout design (max N turns per delegation; configurable)
- `mcp-coder maintenance stats` reports executor turn count per delegation

**Route A (preferred):**
- mcp-coder owns `compile → run(bounded) → inspect → recompile → run` inside one `delegate_to_agent`
- Each sub-run bounded to a small step budget; results inspected before continuing
- File expansion only via spec/policy between steps (D-P4-10 constraint preserved)
- Logs `executor_step_N` events in `delegation_pipeline` and `traces/`

**Route C (fallback only):**
- Extend or wrap Aider `Coder.run()` for per-LLM-turn hooks
- Direct `reasoning_content` capture before Aider strips it
- Higher maintenance; version-coupled to Aider; harder to port to BL-340 (Cursor SDK backend)

**Acceptance:**
- After a live delegate: `traces/<delegation_id>.jsonl` has ≥1 `llm_call` line from executor (separate from helper lines)
- `step_index` field present and monotonic on executor `llm_call` events
- At least one `tool_call` or `action` event per delegation when executor writes files
- `maintenance stats` shows executor turn count per delegation (e.g., `executor_turns: 3`)
- Max step budget respected (configurable; default suggested in master session)
- All existing tests green

**Files touched:** `core/engine/aider_engine.py` (wrap or refactor run loop), `core/observability/` (new event types), `server/mcp_server.py` (orchestrate outer loop), `tests/`

### P7-003 — Compile provenance bundle *(BL-353 remainder)*

**Status:** `open`

**Goal:** Store what went into each pipeline phase — not just flags. At `standard` verbosity, the trace file should contain hashes + brief summaries of each pipeline stage's input/output. At `full` verbosity, full bodies.

**Can run in parallel with P7-002 after P7-001 is done.**

**Scope:**

Pipeline stage provenance events in `traces/<delegation_id>.jsonl`:
- `compile_event` type with `stage` field: `mechanical_brief`, `builder_input`, `builder_output`, `architect_input`, `architect_output`, `validation_input`, `validation_output`, `final_executor_prompt`
- Each event: `sha256` hash + byte count + brief (≤200 chars) at `standard`; full body at `full`; hash-only at `lean`
- Host transcript provenance: `source_path`, byte range, `last_source_line` — enough to slice Cursor JSONL for Phase 8 replay
- RAG hits already covered (lean `context_refs` + DB join — Phase 6 done)

**Acceptance:**
- After a live delegate at `standard` verbosity: `traces/<delegation_id>.jsonl` contains `compile_event` lines for builder, architect, and validation stages
- At `full`: full prompt bodies present
- At `lean`: only hashes
- No regression on existing helper `llm_call` events
- Existing JSONL format unchanged (`delegations.jsonl` lean record untouched)

**Files touched:** `core/engine/context_builder_llm.py`, `core/engine/architect_pass_llm.py`, `core/engine/spec_validation_llm.py`, `core/observability/local.py`, `tests/`
