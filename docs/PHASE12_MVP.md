# Phase 12 — Supervisor as intelligent orchestration layer

**Status:** **Closed** — Phase 12 closed 2026-06-21.
**Purpose:** Transform the SupervisorAgent from a loop-runner into the main intelligence layer of mcp-coder: persistent project memory across delegations, context lifecycle management (continuation briefs, mid-turn enrichment), and pause/resume across host round-trips. All helpers remain stateless; the Supervisor owns all state and routing.
**PM board:** this file · **Issues:** [PHASE12_ISSUES.md](./PHASE12_ISSUES.md)
**Phase 11 (closed):** [PHASE11_MVP.md](./PHASE11_MVP.md) · [PHASE11_ISSUES.md](./PHASE11_ISSUES.md)
**Design notes:** [notes/supervisor-orchestration-layer.md](./notes/supervisor-orchestration-layer.md) · [notes/phase11-master-session-bootstrap.md](./notes/phase11-master-session-bootstrap.md)
**Backlog inputs:** BL-540 (project state), BL-529 (supervisor context window), BL-543 (context lifecycle), BL-544 (pause/resume), BL-541 (reviewer feedback loop), BL-525 (planner v1), BL-542 (context router)

## One-line goal

Give the Supervisor persistent memory of the project, the ability to answer most sub-helper questions autonomously from that memory, and the ability to pause and resume across host round-trips without restarting.

## North-star acceptance (dogfood)

After live `delegate_to_agent` calls across a multi-delegation real project:

1. **Project memory** — after 3 delegations on the same project, `project_state.json` contains: key design decisions, open risks, at least one reviewer finding promoted from a prior delegation. A new delegation's Planner call visibly reads this state (trace event confirms).
2. **Continuation brief** — on a multi-turn delegation (supervisor_max_turns > 1), the executor's turn 2 context includes a `## What happened in turn 1` section that was assembled by the Supervisor — not hallucinated by Aider.
3. **Autonomous interception** — when Clarity asks a question already answered in project state, the Supervisor resolves it without escalating to the host. Logged as `supervisor_intercept` in trace.
4. **Pause/resume** — a delegation that aborts with `needs_input` can be resumed by calling `delegate_to_agent` with `resume_token` + answer. Turn 1 is not re-run. The Planner is not re-invoked. Context is assembled from saved state + the host's answer injected into the brief. This works end-to-end in Cursor.
5. **Reviewer → project state** — a reviewer finding marked `notable` or higher is promoted to `project_state.open_risks`. A subsequent delegation on the same project has it in the Planner's context (Planner output references the risk).
6. **Planner reads history** — when planning for a spec that touches files worked on in a prior delegation, the Planner's context includes the relevant project state summary. Trace shows `planner_context_sources: ["project_state"]`.

## Strategic context

Phase 11 closed with:
- `SupervisorAgent` class with canonical event set and begin/resume API
- `DelegationSupervisor` with in-memory decision log per delegation
- `model_policy` for per-role, per-delegation model overrides
- `answer_delegation_question` — mid-run human gate (experimental)
- Tier-1 reviewer producing structured findings
- Planner pass (`planner_pass`) as a one-shot pipeline phase

**The remaining gap is memory and continuity:**

```
Phase 11:  MCP → [pipeline] → SupervisorAgent loop → result
                                    ↑ no memory of prior delegations
                                    ↑ no project-level context
                                    ↑ every escalation = cold restart next call
```

The Supervisor currently wakes up fresh per delegation. It cannot:
- Know what was decided in the last three delegations
- Answer a Clarity question from project history without asking the human
- Resume where it left off after an escalation
- Give the executor a proper "here's what turn 1 did" handoff for turn 2

Phase 12 closes all four gaps by giving the Supervisor:
1. A durable project state store it owns and maintains
2. A context lifecycle — it assembles the right context for each sub-call from its knowledge
3. Pause/resume — it serializes its session state on escalation and reloads it on resume
4. A feedback loop from the Reviewer back into future planning

**Phase 12 is the shift from "smart loop-runner" to "intelligent project agent":**

```
Phase 11:  SupervisorAgent runs a loop per delegation
Phase 12:  SupervisorAgent maintains project memory + context + continuity across delegations
```

**Phase 12 is NOT:**
- Full multi-agent parallelism (sequential only)
- CTO / Architect role (BL-526) — Phase 13 candidate
- Full executor-pull sidecar HTTP server — deferred (BL-354 full)
- BL-513 AI-suggested params — deferred
- Host chat access for intent inference — noted for later
- Inter-session RAG index of code changes — deferred (BL-333)

## Cross-phase architectural decisions

*(New decisions added in Phase 12 planning. D-ARCH-1..D-ARCH-6 from Phase 11 remain in force.)*

| ID | Decision |
|----|----------|
| **D-ARCH-7** | **Supervisor is the sole owner of session and project state.** No helper writes to `project_state.json` directly. Reviewer returns findings → Supervisor decides what to persist. Planner returns a plan → Supervisor extracts durable decisions and writes them. State writes are auditable and funneled through the Supervisor. |
| **D-ARCH-8** | **Interception before escalation.** When a sub-helper generates a blocking question (Clarity, `confirm_ask`, spec validation), the Supervisor intercepts first: checks decision_log, project_state, plan. Only questions it cannot resolve from known context escalate to the host. Goal: minimize human interruptions without hiding important decisions. Every intercept is logged (`supervisor_intercept` event). |
| **D-ARCH-9** | **Pause/resume preserves pipeline work.** On pause, Supervisor serializes full session state with a `resume_token` (stored in `supervisor_states/<token>.json`). On resume: clarity_check, spec_validation, context_compile, planner_pass, completed executor turns are **not re-run**. The host's answer is injected into the continuation brief for the next turn. The Planner may revise the remaining plan if the answer changes scope. |
| **D-ARCH-10** | **Multi-model Supervisor by decision weight.** The Supervisor selects model tier based on the cognitive demand of each internal decision (see design note for tier table). Configured via `model_policy` extension. The Supervisor selects its own internal model; the host can override the whole policy per delegation. |
| **D-ARCH-11** | **Two-tier Supervisor context model (extends D-ARCH-1).** Supervisor context has two tiers: **Tier 1** (slow-changing, assembled once per turn) — spec text, plan, decision log tail, task description. **Tier 2** (action-specific, on demand) — the Supervisor's LLM calls tools based on its own reasoning to pull additional context (`get_delegation_history`, `get_project_state`, `read_file`, `get_diff`, `get_reviewer_findings`). Tool calls logged as `supervisor_tool_call` events. D-ARCH-1 frugality still applies: tool results are truncated to per-tool budgets; total context window per LLM call stays within budget even with tool results. |

## Locked design decisions

| ID | Decision |
|----|----------|
| D-P12-1 | **`project_state.json` schema is append-friendly and versioned.** Structure: `decisions[]`, `open_risks[]`, `hot_areas[]`, `reviewer_findings_summary[]`, `last_updated`. Reads are non-blocking (file may not exist on first delegation — treated as empty). Writes are atomic (write to `.tmp`, rename). Schema version field for forward compat. |
| D-P12-2 | **Project key is derived from spec_path prefix, not MCP session.** Ensures project state survives Cursor restarts. Key = first two segments of spec path relative to repo root (e.g., `tasks/auth` from `tasks/auth-01.md`). Configurable override via `MCP_CODER_PROJECT_KEY`. |
| D-P12-3 | **Continuation brief is assembled by the Supervisor, not Aider.** After each completed executor turn, the Supervisor reads `files_changed` + `output_tail` + `reviewer_findings` and writes a structured brief. This brief is prepended to the next turn's context. Aider never "knows" it is in a multi-turn delegation — the Supervisor manages that abstraction. |
| D-P12-4 | **`resume_token` on `delegate_to_agent` is optional and backward-compatible.** If absent: fresh delegation (current behavior). If present: load state and resume. Invalid/expired token: return `error: resume_token_expired` with clear message. Token TTL configurable via `MCP_CODER_RESUME_TOKEN_TTL` (default `86400` seconds). |
| D-P12-5 | **Reviewer findings classification is Supervisor-owned.** After each `reviewer_pass`, the Supervisor classifies findings as `advisory | notable | critical`. Only `notable` and `critical` are promoted to `project_state.open_risks`. `advisory` findings stay in the spec report only. Classification prompt uses spec contract as reference to calibrate severity. |
| D-P12-6 | **Planner v1 uses pre-injection, not tool-calling loop.** P12-005 injects a `## Project state` section into the existing planner prompt before the LLM call (compressed decisions + open risks touching current spec files, max ~800 tokens). No `SupervisorToolRunner` wrapping for the Planner in Phase 12. Full tool-calling Planner is BL-525 complete / Phase 13. After planning, Supervisor extracts explicit decisions from plan text and writes them back to project state. |
| D-P12-7 | **get_delegation_history uses workspace_history.db via list_delegations().** No new delegation index needed. Tool queries `snapshots` table filtered by `spec_path`, returns last N compact summaries. get_diff is out of Phase 12 scope — files_changed list + read_file are sufficient for supervisor routing decisions. |
| D-P12-8 | **SupervisorToolRunner extends gateway.complete() with tools= param.** Add `tools: list | None` to `gw.complete()` and `tool_calls: list | None` to `GatewayCompletion`. SupervisorToolRunner calls gw.complete() directly. All other helper LLM calls unchanged. Text-based tool protocol (model-emits-JSON) not used. |

## Milestones

### P12-001 — Stateful SupervisorAgent + pause/resume *(BL-544 + session state from BL-540)*

**Status:** `shipped` (2026-06-21, commit 16dfe7b + follow-ups)
**Goal:** Refactor `SupervisorAgent` to maintain serializable session state. On escalation (`needs_input`), save state and support resume without re-running completed pipeline stages. Host answer injected on resume (implicit resume via `answer=`; P12-ISS-001).

This is the structural foundation.

**Scope:**
- `core/engine/supervisor_agent.py` — refactor `SupervisorAgent` to carry a `SupervisorState`:

  ```python
  @dataclass
  class SupervisorState:
      resume_token: str            # UUID4
      spec_path: str | None
      project_key: str             # derived from spec_path; see D-P12-2
      turn_index: int              # number of completed turns
      plan: str | None             # from planner_pass (None if planner didn't run)
      decision_log: list[dict]     # all confirm_ask decisions from completed turns
      completed_turn_artifacts: list[dict]  # {files_changed, output_tail} per turn
      pause_reason: str            # "needs_input" | "max_turns_reached"
      questions: list[str]         # questions for the host
      context_ref: str             # delegation_id → context package on disk
      paused_at: str               # ISO8601
      expires_at: str              # ISO8601 (paused_at + TTL)
  ```

  - `SupervisorState.save(base_dir)` → `<base_dir>/projects/<project_key>/supervisor_states/<token>.json` (atomic write: tmp + rename)
  - `SupervisorState.load(token, base_dir)` → raises `ResumeTokenExpired` | `ResumeTokenNotFound`
  - `SupervisorState.base_dir()` → `~/.mcp-coder` (or `MCP_CODER_HOME` env)
  - `ProjectKeyResolver.from_spec_path(spec_path)` — first 2 path segments relative to repo root; `MCP_CODER_PROJECT_KEY` env override; falls back to `"default"` if spec_path is None

- `SupervisorAgent` API changes:
  - `begin(...)` — existing entry point; initializes fresh `SupervisorState`
  - `SupervisorAgent.resume(state: SupervisorState, host_answer: str)` — new class method; bypasses pipeline; reloads decision log and turn artifacts; injects `host_answer` into executor context for next turn; continues loop from `state.turn_index`
  - On `needs_input` escalation: save state → attach `resume_token` to `DelegationResult`

- `server/mcp_server.py`:
  - New optional `resume_token: str | None = None` param on `delegate_to_agent`
  - New optional `answer: str | None = None` param (the host's answer to the paused questions)
  - If `resume_token` present: `SupervisorState.load(token)` → `SupervisorAgent.resume(state, answer)` → skip full pipeline
  - Error handling: expired token → `DelegationResult(outcome="error", error="resume_token_expired")`; missing token → `"resume_token_not_found"`
  - Existing behavior unchanged when `resume_token` is absent

- `DelegationResult` / response schema:
  - Add `resume_token: str | None` field (populated only when `outcome == "needs_input"`)
  - Add `paused_questions: list[str] | None` field (same condition)

- Env: `MCP_CODER_RESUME_TOKEN_TTL` (seconds, default `86400`)

- Trace events:
  - `supervisor_paused` — on state save: `{resume_token, turn_index, pause_reason, questions, expires_at}`
  - `supervisor_resumed` — on state load: `{resume_token, resumed_at_turn, project_key, host_answer_chars}`
  - `resume_token_expired` — when load fails due to TTL: `{resume_token, expired_at}`

- Tests (≥ 12 required):
  - Fresh delegation: no resume_token in params → full pipeline runs; `resume_token` in result on `needs_input` escalation
  - `SupervisorState.save()` is atomic (tmp + rename); file exists after save
  - `SupervisorState.load()` restores all fields; TTL check raises `ResumeTokenExpired` when expired
  - `ProjectKeyResolver.from_spec_path()`: correct key for standard path; env override respected; `None` path → `"default"`
  - Resume: `delegate_to_agent(resume_token=..., answer=...)` → planner NOT called; clarity NOT called; context compile NOT called; `supervisor_resumed` event in trace
  - Resume: `turn_index` starts from saved value; `decision_log` populated from saved state
  - Resume: host answer injected into executor context (appears in `executor_context` or trace field)
  - Expired token: `delegate_to_agent(resume_token=<expired>)` → `outcome="error"`, `error="resume_token_expired"`
  - Missing token: `outcome="error"`, `error="resume_token_not_found"`
  - `DelegationResult` has `resume_token` when `outcome="needs_input"`, absent otherwise
  - Multi-turn: turn 1 completes → turn 2 starts → `completed_turn_artifacts` has turn 1 entry
  - State directory created if it doesn't exist

**Files policy:**
- **Must touch:** `core/engine/supervisor_agent.py`, `server/mcp_server.py`
- **New:** `core/engine/supervisor_state.py` (or inline in `supervisor_agent.py` if small), `core/state/` directory (for `project_key.py` resolver)
- **May touch:** `core/engine/aider_engine.py` (to pass `host_answer` into context if needed), delegation result schema
- **Must not touch:** `core/config/`, `core/context/`, `core/specs/`, any CLI, any viewer

**Acceptance:**
- `delegate_to_agent` with an escalating task returns `needs_input` + `resume_token` + `paused_questions`
- `delegate_to_agent(resume_token=..., answer=...)` runs the next executor turn without re-running planner or context compilation; `trace inspect` shows `supervisor_resumed` event
- Expired / missing token returns structured `DelegationResult` error, not an exception stack trace
- Full test suite passes (≥ 12 new tests in `tests/test_supervisor_state_p12_001.py`; no regressions in `test_supervisor_agent_p12_001.py` or broader suite)

### P12-003 — `SupervisorToolRunner`: two-tier context + tool-calling loop *(BL-530, BL-542)*

**Status:** `shipped` (2026-06-21, commit 367ba27)

**Two-tier model:**
- **Tier 1 (base, always present):** spec text (compressed), current plan, decision log tail, task description. Assembled once per turn start or delegation resume.
- **Tier 2 (on demand, via tool calls):** the Supervisor's LLM reasons about what additional context it needs and issues tool calls. The `SupervisorToolRunner` executes them and appends results before the next LLM iteration.

**Scope:**
- `core/engine/supervisor_tool_runner.py` — new `SupervisorToolRunner`:
  - `register_tool(name, description, schema, fn)` — registers a callable with its function-spec definition
  - `run(system_prompt, messages)` → iterates: LLM call → if tool call: execute + append result → repeat until final decision or `max_tool_rounds` exceeded (default 3)
  - Falls back to single-call behavior if model doesn't support function calling
  - Trace events: `supervisor_tool_call` per tool invocation: `{tool, args_summary, result_tokens, duration_ms}`
- Built-in Phase 12 tools (registered at `SupervisorAgent` construction):
  - `get_project_state()` → summary from `ProjectState` (P12-002)
  - `get_delegation_history(spec_path, n=3)` → last N delegation summaries from `delegations.jsonl`
  - `read_file(path)` → file content (truncated to budget)
  - `get_diff(delegation_id)` → unified diff from a past delegation's `files_changed`
- Wire `SupervisorToolRunner` into both decision paths:
  - `DelegationSupervisor._evaluate()` (confirm_ask decisions)
  - `SupervisorAgent._llm_decide()` (inter-turn decisions)
- Tier-1 base context assembled once at turn start; stored in `SupervisorState.base_context` (wired from P12-001) so it survives pause/resume without recompilation
- Tests: tool registered and callable; `supervisor_tool_call` event emitted; tool result appended to conversation; max_tool_rounds fallback fires; single-call fallback when function-calling unsupported; tier-1 assembled once, not re-assembled per confirm_ask

**Acceptance:**
- `trace inspect <id>` shows `supervisor_tool_call` events when Supervisor needed extra context
- On a delegation where a spec file was last modified in a prior run, Supervisor calls `get_delegation_history` and references it in its decision reasoning
- Full suite passes; `DelegationSupervisor` and `SupervisorAgent._llm_decide` use `SupervisorToolRunner`
