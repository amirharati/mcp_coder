# Phase 11 — Supervised execution + smarter context

**Status:** **Active** — Phase 11 opened 2026-06-18.
**Purpose:** Make the Aider/MCP relationship qualitatively more powerful: supervised execution (Aider is no longer a blind `yes=True` process), smarter context before delegation, and output quality gates — all while keeping per-delegation cost bounded through context frugality.
**PM board:** this file · **Issues:** [PHASE11_ISSUES.md](./PHASE11_ISSUES.md)
**Phase 10 (frozen):** [PHASE10_MVP.md](./PHASE10_MVP.md) · [PHASE10_ISSUES.md](./PHASE10_ISSUES.md)
**Design notes:** [notes/phase11-master-session-bootstrap.md](./notes/phase11-master-session-bootstrap.md)
**Backlog inputs:** BL-351 (supervised IO full), BL-521 (clarity pass, new), BL-354 (executor-pull v0), BL-358 (reviewer v0), BL-512 (host model policy), BL-522 (mid-run human gate, new)

---

## One-line goal

Give the executor a supervisor that can think, give the host a way to pass intent clearly, and give the output a lightweight quality gate — without blowing up per-delegation cost.

## North-star acceptance (dogfood)

After live `delegate_to_agent` calls in a real project:

1. **Supervised execution** — when Aider's `confirm_ask` fires (shell command, out-of-scope file add, scope expansion), a supervisor LLM reads the spec contract and decides approve / deny / abort rather than blindly saying yes.
2. **Decision audit** — every supervisor decision is logged in the trace (`supervisor_decision` event) with the question, decision, and reasoning. Accessible via `trace inspect`.
3. **Clarity pass** — before a delegation with an ambiguous spec, the clarity pass returns `clarification_needed` with 2–3 targeted questions. After answering, the delegation runs and does not stall on the same ambiguity.
4. **Executor-pull hints** — Aider's system prefix instructs it to use `/read` for additional context rather than asking to "add files to chat", reducing `needs_input` stalls.
5. **Tier-1 reviewer** — after a successful delegation, changed files are scanned by a cheap model and a brief review note is appended to the spec report (docstrings, obvious gaps, import issues).
6. **Host model policy** — Cursor can pass `model_policy: {supervisor: {model: "..."}, executor: {thinking_budget: 8000}}` per `delegate_to_agent` call to tune behavior per task without changing env vars.
7. **Mid-run human gate (experimental)** — when supervisor judges human input is required, an `answer_delegation_question` MCP tool call from Cursor unblocks the Aider thread and continues the delegation in-flight. (Requires Cursor concurrent tool call support; falls back to abort-and-resume if not supported.)

## Strategic context

Phase 10 closed the "blind delegation" gaps at a POC level: you can see what's happening (`logs tail`), executor behavior is shapeable (`system_prompt_prefix`), and stalls produce structured `needs_input` rather than silent failure.

**The remaining gap is control and quality:**
- Aider still runs with `yes=True` — it auto-approves every decision without mcp-coder judgment
- No pre-flight check on whether the task is clear enough to delegate confidently
- No post-flight quality scan — delegation output is whatever Aider produced
- Cursor has no per-call control over which models run at what budget
- The Aider ↔ MCP relationship is thin: one context bundle in, one result out

Phase 11 closes these gaps by making the Aider/MCP boundary **bidirectional and supervised**:

```
Phase 10:  MCP → Aider (fire and forget, yes=True) → result
Phase 11:  MCP → Aider (supervised, decisions routed) ↔ Supervisor LLM → result → reviewer
```

**Phase 11 is NOT:**
- Full outer-loop plan/resume (multi-step plan object with async resume) — Phase 12
- Tier-2 epic-boundary review (needs epic boundary concept) — Phase 12
- BL-513 AI-suggested params (heuristic only in P11) — Phase 12 full version
- BL-514 dynamic escalation mid-delegation — Phase 12
- Full executor-pull sidecar server — Phase 12

## Cross-phase architectural decisions

*(These decisions span Phase 11 and beyond. Workers must not violate them.)*

| ID | Decision |
|----|----------|
| **D-ARCH-1** | **Context frugality rule.** Every LLM call in the pipeline gets a purpose-built context bounded to its role. No LLM call sees the full session state. Supervisor: ~2k tokens (spec + question + tail). Reviewer: diff + changed files only. Clarity pass: task + spec + delegation titles. This is a platform principle, not a single-phase decision. |
| **D-ARCH-2** | **Strong LLM for judgment calls.** The supervisor LLM that approves/denies/aborts Aider decisions is configurable and defaults to a mid-to-strong tier (Sonnet-class), not cheap. Cost is bounded by D-ARCH-1 (small context, few calls per delegation). |
| **D-ARCH-3** | **Aider thread stays alive through supervised IO.** The `SupervisedIO` subclass blocks the Aider thread at `confirm_ask()` and returns a decision. No restart, no re-run — the coder instance continues from where it paused. This exploits the existing executor session cache (P2-210 / P9). |
| **D-ARCH-4** | **Per-delegation supervisor state (in-memory decision log).** `DelegationSupervisor` maintains a decision log per delegation run. Each supervisor call receives: spec contract + architect plan + prior decisions + current question + output tail. Log is compact (one entry per decision). Persisted to trace at delegation end. |
| **D-ARCH-5** | **Human escalation v1 = abort-and-resume (Phase 11). Mid-run gate is experimental.** Default path: supervisor aborts cleanly with `needs_input` when human judgment is required. The `answer_delegation_question` tool (P11-004) is experimental and depends on Cursor concurrent tool call support. Degrade gracefully. |
| **D-ARCH-6** | **model_policy arg is additive (host > env > code defaults).** BL-512 Stage 2. Host-passed policy overrides env layer for that delegation only. Each role (supervisor, executor, reviewer, etc.) is independently configurable. |

## Locked design decisions

| ID | Decision |
|----|----------|
| D-P11-1 | **SupervisedIO classifies confirms by risk tier.** Low-risk (routine file writes, standard edits) → auto-approve without supervisor call. High-risk (shell commands, out-of-scope file adds, deletions) → supervisor LLM. Unknown → supervisor LLM. This avoids supervisor overhead on every trivial confirm. |
| D-P11-2 | **Supervisor model is `MCP_CODER_SUPERVISOR_MODEL`, defaults to same as ROLE_CONTEXT_BUILDER but overridable.** Separate from executor model so host can tune independently. In `model_policy`, supervisor is a first-class role. |
| D-P11-3 | **Clarity pass is a new pipeline phase `clarity_check`, opt-in via `clarity_pass: true` (yaml/env).** Not always-on in Phase 11 — need dogfood evidence on false-positive rate before making default. Returns early with `clarification_needed` if confidence below threshold. |
| D-P11-4 | **Executor-pull v0 = system prefix instruction only.** Aider is instructed via `system_prompt_prefix` to use `/read <path>` for additional context instead of asking to "add files to chat". This uses the already-shipped P10-001 infrastructure with zero new code. Full sidecar HTTP tool server (BL-354 full) is Phase 12. |
| D-P11-5 | **Tier-1 reviewer is opt-in in Phase 11** (`reviewer_pass: true` in spec or `MCP_CODER_REVIEWER_PASS=1`). Default off while we measure quality delta. Runs on `files_changed` only — not full codebase. Uses cheap model (Flash/Haiku tier). Appended to spec report, not a separate delegation. |
| D-P11-6 | **`answer_delegation_question` tool uses a threading.Event keyed by `delegation_id`.** When the supervisor flags human escalation, it posts the question to an in-process registry and emits `ctx.info`. The answer tool (if called concurrently by Cursor) sets the event and the Aider thread unblocks. On timeout (default 120s), supervisor falls back to abort-and-resume. |
| D-P11-7 | **Smart architect trigger: on by default, skip heuristic.** Architect pass runs unless: `len(target_files) < 2` AND no `epic_step: true` in spec AND no architecture keywords in task. Override with `architect_pass: true/false` in spec. Replaces current global env toggle as the primary control. |

## Milestones

### P11-001 — Spec clarity pass v0 *(BL-521)*

**Status:** `done` — shipped 2026-06-19 (uncommitted; 16 tests in `test_clarity_pass_p11_001.py`)
**Goal:** Before delegating, run a cheap LLM call that checks whether the task description and spec are clear enough to proceed. If ambiguous or missing key decisions, return `clarification_needed` with targeted questions rather than running an executor that will stall.

**Scope:**
- New pipeline phase `clarity_check` inserted before `compile` when `clarity_pass: true` (yaml) or `MCP_CODER_CLARITY_PASS=1` (env)
- Cheap model (Flash-class), small context: task + spec Files section + last 3 delegation titles in session
- Prompt: "What is unclear or missing? List at most 3 specific questions. If nothing is unclear, return CLEAR."
- On `CLEAR` → proceed normally, zero latency overhead beyond the LLM call
- On questions → return `clarification_needed: [...]` early (same field as BL-329 spec validation)
- Distinct from BL-329 spec validation: validation checks coherence against transcript; clarity pass checks task completeness
- Audit: `clarity_check_result` in delegation trace (`clear | clarification_needed | skipped`)
- Tests: clarity pass fires when task is vague; skips when `clarity_pass: false`; `clarification_needed` returned without running executor

**Acceptance:**
- Delegation with vague task ("fix the auth stuff") → clarity pass returns 2–3 questions
- Delegation with clear spec → clarity pass returns `CLEAR`, executor runs normally
- `trace inspect` shows `clarity_check_result` event

### P11-002 — Supervised executor v1 *(BL-351 full)*

**Status:** `done` — shipped 2026-06-19 (uncommitted; 15 tests in `test_supervised_io_p11_002.py`)
**Goal:** Replace blind `yes=True` with a `SupervisedIO` subclass that routes Aider's `confirm_ask` decisions to a `DelegationSupervisor` LLM. The supervisor reads the spec contract, prior decisions, and current context to approve / deny / abort — not blindly approve.

**Scope:**
- `core/engine/supervisor.py` — new `DelegationSupervisor` class:
  - In-memory `decision_log: list[dict]` per delegation
  - Builds context: spec contract + architect plan + decision log + executor output tail + current question (~2k tokens)
  - Calls supervisor LLM (`MCP_CODER_SUPERVISOR_MODEL`, default same tier as context builder)
  - Returns: `approve | deny | abort | escalate`
  - Escalation path v1: abort cleanly, return `needs_input` with supervisor reasoning
- `core/engine/supervised_io.py` — `SupervisedIO(InputOutput)`:
  - Classifies `confirm_ask` by risk tier: low-risk (auto-approve), high-risk / unknown (supervisor)
  - Blocks Aider thread, calls supervisor synchronously from worker thread
  - Passes decision back to Aider; run continues uninterrupted on approve
- `core/engine/aider_engine.py` — swap `InputOutput` for `SupervisedIO` when `supervised_execution: true` (yaml) or `MCP_CODER_SUPERVISED_EXEC=1`
- Trace events: `supervisor_decision` event per confirm_ask decision (question, decision, reasoning, duration_ms)
- Delegation record: `supervisor_decisions_count`, `supervisor_aborts_count` audit fields
- Tests: supervisor fires on shell command confirm; auto-approves low-risk file write; abort path returns structured `needs_input` with supervisor reasoning

**Acceptance:**
- Delegation where Aider tries to run `npm install` → supervisor checks spec, approves or denies with logged reasoning
- Delegation where Aider asks to add out-of-spec file → supervisor denies, returns `needs_input`
- `trace inspect <id>` shows all `supervisor_decision` events

### P11-004 — Mid-run human gate *(BL-522, experimental)*

**Status:** `done` — shipped 2026-06-19 (30 tests: 15 new + 15 supervised regression)
**Goal:** When the supervisor determines human input is required, an `answer_delegation_question` MCP tool call from Cursor unblocks the Aider thread in-flight. No restart, no re-run — the coder continues from where it paused.

**Scope:**
- `core/engine/question_registry.py` — in-process registry: `{delegation_id: {question, event: threading.Event, answer: str | None}}`
- `SupervisedIO` escalation path: posts to registry, emits `ctx.info` with question + delegation_id, then `event.wait(timeout=120)`
- On timeout: falls back to abort-and-resume (P10-003 pattern)
- New MCP tool `answer_delegation_question(delegation_id: str, answer: str)`: looks up registry, sets answer, sets event
- Trace events: `supervisor_human_gate_opened`, `supervisor_human_gate_answered | supervisor_human_gate_timeout`
- Tests: event bridge unblocks Aider thread; timeout path falls back to abort; registry cleaned up after delegation

**Acceptance:**
- With Cursor calling `answer_delegation_question` concurrently: Aider resumes with human answer
- Without concurrent call: times out cleanly, returns `needs_input` as usual
- No deadlocks, no leaked threads

**Note:** This is experimental. If Cursor's MCP client does not support concurrent tool calls from the same session, the timeout path will always trigger. Dogfood will determine whether this is usable or needs protocol-level support.

### P11-007 — Host model policy (BL-512 Stage 2)

**Status:** `done` — shipped 2026-06-19 (36 tests passed; 41 with helper-path regression checks)
**Goal:** Cursor (or any host) can pass a `model_policy` object in `delegate_to_agent` args to tune which model and parameters are used for each role in that delegation — without restarting the MCP server or changing env vars.

**Scope:**
- New optional `model_policy: dict | None` arg on `delegate_to_agent`

  ```json
    "reviewer":    {"model": "..."},

  ```
- Precedence: host policy > env vars > code defaults (D-ARCH-6)
- `core/config/model_registry.py` — extend `resolve()` to accept optional `host_policy_override: dict`; inject between env and code-default layers
- Audit: `model_policy_applied` event in trace showing which roles were overridden
- Tests: host policy overrides env for executor; non-overridden roles use env; invalid policy fields are ignored with warning

**Acceptance:**
- Delegation with `model_policy: {executor: {thinking_budget: 12000}}` → executor uses high thinking budget
- Delegation without `model_policy` → unchanged behavior
- `trace inspect` shows `model_policy_applied` with override fields
