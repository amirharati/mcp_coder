# Phase 14 — Supervisor intelligence + logging depth

**Status:** **Active** — opened 2026-06-23.
**Purpose:** Convert the Supervisor from a structural skeleton into a minimally intelligent agent: give it context, make its control loop use that context, verify helper LLMs and configs are correct, and deeply audit the logging/viewer stack so everything the Supervisor decides is captured and visible. Not a feature phase — a trust phase. Output feeds Phase 15 MVP usage decision (adopt or pause).
**PM board:** this file · **Issues:** [PHASE14_ISSUES.md](./PHASE14_ISSUES.md)
**Phase 13 (closed):** [PHASE13_MVP.md](./PHASE13_MVP.md) · [PHASE13_ISSUES.md](./PHASE13_ISSUES.md)
**Design notes:** [notes/supervisor-agent-architecture.md](./notes/supervisor-agent-architecture.md) · [notes/system-design-overview.md](./notes/system-design-overview.md)

## One-line goal

Make the Supervisor actually think — give it context to reason over, a control loop that uses that context, clean helper inputs, and a logging stack that captures and shows everything it does.

## North-star acceptance

After Phase 14:

1. **Supervisor has context** — `DelegationSupervisor.evaluate()` receives spec contract + plan + decision log + executor output tail + compact `project_state` summary per decision. Trace shows the context block.
2. **Control loop uses intelligence** — at least one class of `confirm_ask` (file-in-spec approve) is handled autonomously; reviewer findings are injected into turn 2+ continuation brief when `max_turns>1`. Trace shows `supervisor_intercept` events with reasoning.
3. **Helper LLMs + configs audited** — planner/reviewer/builder/supervisor prompts reviewed and fixed where weak; LLM configs (streaming, reasoning/thinking tokens, provider-specific options like OpenRouter `reasoning` param) verified and wired for the dogfood provider. Reasoning tokens captured for all roles where the provider supports them.
4. **Logging is deep and clean** — capture completeness verified across all roles (every `llm_call` has matching proxy/backend events); viewer parity verified (no silently dropped event types or fields after P13-008 fixes); cleanliness audited (no duplicate emissions, no orphan rows, no silent error swallowing). Findings fixed or filed as P14-ISS-*.

## Strategic context

Phase 13 shipped the **structural** Supervisor (lifecycle envelope, checkpoint, pause/resume, project state) and proved it in CLI dogfood. But the Supervisor is **not yet intelligent**: it sees almost nothing per decision (`question` + `risk_tier` + `target_files`), escalates every `confirm_ask` to the host, and its reasoning is partially invisible in traces.

Phase 14 closes the **trust gap** between "structurally correct" and "intelligent enough to use on a real project." This is the highest-leverage work toward MVP usage (Phase 15 adopt/pause decision).

**Phase 14 is NOT:**
- Full autonomous interception policy (BL-547 full vision)
- Full continuation brief assembly (BL-543 full)
- Executor-pull RAG sidecar (BL-354)
- Planner-as-full-agent loop (BL-525)
- Architect/CTO role (BL-526)
- Product UI or spec MCP tools

Those stay in backlog. Phase 14 deepens the spine, not the vision surface.

## Milestones

### P14-003 — Helper LLM + prompt + config audit

**Status:** `3b+3c done` (2026-06-24) — 3a prompt audit still pending as separate `P14-003a` spec.
**Goal:** Review and fix the prompts and LLM configs for all helper roles (planner, reviewer, builder, supervisor, clarity, spec_validation) and the Aider executor. Verify provider-specific options (streaming, thinking tokens, capabilities) are wired correctly for the dogfood provider.

**Scope:**

**Order:** **3b → 3c → 3a** (not the listing order). Fix streaming/thinking-token wiring first so 3a prompt changes can be tested against real reasoning output.

**3a. Prompt audit:**
- Planner prompt — is it producing real plans or restating the task?
- Reviewer prompt — is it catching real issues or generating noise? (P13 saw false criticals)
- Builder brief — is it useful context or paraphrased spec?
- Supervisor prompt — is it asking the right question for `confirm_ask` decisions?
- Clarity / spec_validation prompts — are they blocking on real ambiguity?
- **Inline-fix vs. ISS threshold:** one-line / format / obvious-weakness → fix inline; structural redesign or behavior change → file as P14-ISS-*. (Examples: planner restating task → ISS; reviewer typo → inline; reviewer false-critical redesign → ISS.)

**3b. LLM config audit:**
- Verify `MCP_CODER_EXECUTOR_REASONING_EFFORT` / `MCP_CODER_EXECUTOR_THINKING_BUDGET` / `MCP_CODER_EXECUTOR_EXTRA_PARAMS` are actually wired to the provider call (not just parsed and ignored).
- Verify OpenRouter-specific options (e.g. `reasoning` param for Anthropic models, `include_usage` for streaming) are enabled where needed to capture thinking tokens.
- Verify streaming is enabled for roles where it matters (executor, supervisor) and that `stream_options: include_usage` is set so token counts are captured.
- Verify `MCP_CODER_CAPTURE_REASONING` is actually respected for every role, not just some. **This is itself part of the audit (find-and-fix), not assumed-done** — grep `capture_reasoning_enabled` call sites and confirm every helper role's call site gates on it.
- Check for provider-specific quirks: Anthropic extended thinking, OpenAI o-series reasoning, OpenRouter passthrough params.
- Verify Aider's own model config (`--stream`, `--model`, weak model) is compatible with our capture layer.

**3c. Reasoning token capture verification:**
- Run a delegation with each helper role enabled using the dogfood provider: **`openrouter/anthropic/claude-sonnet-4.5`** for helper roles (supervisor/planner/reviewer/clarity/builder); executor stays on its current dogfood model (`openrouter/google/gemini-2.5-flash`) so capture deltas are attributable to the helper path. A second end-to-end run with executor on Sonnet is optional, for executor-side thinking capture verification.
- For each `llm_call` event, check `reasoning_tokens` is populated (or explicitly absent if the provider doesn't support it).
- Check whether `.mcp-coder/test-thinking/traces/` already contains a prior thinking-token test run; if so, use as a starting baseline.
- File gaps as P14-ISS-*.

**Test traffic convention:** create a throwaway spec under `.mcp-coder/specs/tasks/p14-003c-capture-test.md` (same shape as the existing `p11-log-gate-test.md` — minimal single-file edit, purpose-built to generate a delegation with minimal side effects).

**Acceptance:**
- Obvious prompt weaknesses fixed.
- LLM configs verified end-to-end for at least one provider (OpenRouter + Anthropic model recommended for thinking token coverage).
- Reasoning tokens captured for every role where the provider supports them.
- Findings documented in § Results; larger items filed as P14-ISS-* or backlog.

**Depends on:** nothing (entry point). **Feeds:** P14-001 (clean inputs), P14-004 (test traffic).

### P14-001 — Supervisor context window v1

**Status:** `done` (2026-06-24) — plan→implement split executed cleanly.
**Goal:** Give `DelegationSupervisor.evaluate()` enough context to judge `confirm_ask` questions meaningfully.

**Scope reality check (2026-06-23):** `core/engine/supervisor.py::build_supervisor_prompt()` **already accepts and wires** `spec_contract`, `architect_plan`, `prior_decisions`, and `output_tail`. So the context block is not being built from scratch — most of it is already there. The genuinely missing pieces are:

1. **`project_state` summary** — cross-delegation memory (decisions, hot areas, reviewer finding summaries). Not currently passed to `build_supervisor_prompt`.
2. **Structured `target_files`** — the Supervisor needs the contract's file list as a structured field (not just prose in `spec_contract`) so it can match "add file X?" against the contract without parsing. Currently `target_files` reaches `SupervisedIO` but not the supervisor prompt as a structured section.

**The actual work in P14-001:**

| Slice | What | Where |
|-------|------|-------|
| **Verify** | Confirm `build_supervisor_prompt`'s already-wired fields (`spec_contract`, `architect_plan`, `prior_decisions`, `output_tail`) are actually populated with real values at call sites — not silently passed as `None`/empty. | `core/engine/supervisor.py` + callers (likely `core/engine/supervised_io.py` and `core/pipeline/phases.py`) |
| **Add** | `project_state` summary section — compact (decisions + hot areas + risks), bounded to ~500 tokens. | `build_supervisor_prompt` signature + caller |
| **Add** | Structured `target_files` section — the contract's `files_edit` + `files_read` as a plain list, so "add file X?" can be matched without parsing prose. | `build_supervisor_prompt` signature + caller |

**Bounded to ~2–4k tokens total** — not full session history, not RAG-fed, just enough to judge the question in front of it.

**Not solved (stays partial):**
- Full continuation brief assembly for turn 2+ (BL-543 C full)
- RAG-fed Supervisor context
- Topic-based context refresh
- Dynamic context rebuilding

**Acceptance:**
- Call-site audit: every already-wired field is confirmed populated (or the gap filed as P14-ISS-*).
- `project_state` summary and structured `target_files` added to `build_supervisor_prompt`; trace shows them on `supervisor_decision` events.
- A delegation where Aider asks "add file X?" and X is in spec Files → Supervisor can see that X is in scope (even if interception logic isn't shipped yet in P14-001).

**Depends on:** P14-003 (clean inputs). **Feeds:** P14-002 (control loop uses context).

### P14-002 — Supervisor control loop — autonomous interception + reviewer findings injection

**Status:** `done` (2026-06-24) — plan→implement split executed cleanly; 17 new tests pass.
**Goal:** Make the Supervisor actually use its context (from P14-001) to act, not just escalate. Two coupled slices:

**2a. Autonomous interception v1 (BL-547 v1):**

Classify `confirm_ask` questions and handle the easy cases:
- "Add file X?" where X is in spec `files_edit` or `files_read` → **approve** (with reason in trace)
- "Add file X?" where X is clearly out of scope → **deny** (with reason in trace)
- Ambiguous / needs human judgment → **escalate** (current behavior, preserved)

Emit `supervisor_intercept` trace event with: classification, decision, reasoning, context block reference.

**2b. Reviewer findings injection (BL-543 C start):**

When `max_turns>1` and reviewer returns findings:
- Inject a compact "## Reviewer findings" block into the next turn's continuation brief
- Supervisor decides: address findings (rerun) or accept (finish)
- Trace shows the findings block in the turn 2+ context

**Not solved (stays partial):**
- Richer interception policy (learning from past decisions, project_state-driven answers for non-file questions)
- Full continuation brief assembly
- Dynamic context rebuild
- BL-546 executor session adaptation

**Acceptance:**
- At least one `confirm_ask` class (file-in-spec approve) handled autonomously; trace shows `supervisor_intercept` with reasoning.
- A `max_turns=2` delegation with reviewer findings visibly injects findings into turn 2 brief; trace shows it.
- Escalation path preserved for ambiguous cases.

**Depends on:** P14-001 (context). **Feeds:** P14-004 (new events to verify captured/visible).

### P14-004 — Logging depth audit + viewer parity

**Status:** `pending`
**Goal:** Deeply verify that the logging stack captures everything and the viewer shows everything captured. Not a surface check — a systematic audit across all event types, fields, and roles.

**Scope:**

**4a. Capture completeness (find-and-fix):**
- Run a delegation with every role enabled (clarity, spec_validation, planner, builder, executor, supervisor, reviewer).
- For each `llm_call` event, verify matching `proxy_llm_call` and `backend_llm_call` exist.
- Verify `reasoning_tokens` populated for every role where the provider supports it (ties to P14-003c).
- Check for LLM calls that happen but emit no trace event (Aider weak model, retries, internal calls).
- Fix gaps inline where trivial; file as P14-ISS-* where larger.

**4b. Viewer parity (find-and-fix):**
- Generate the full set of event types the system can emit (grep `emit_` / `trace_event(` / `record(` across `core/`).
- For each event type, verify there's a handler in `delegation_view_enrich.py::_build_view_events()`.
- For each handler, verify it surfaces the **fields** that exist in JSONL (not just the event type — a handler that renders an event but drops fields is still a silent gap).
- Check truncation points — where does the viewer clip text that exists in full on disk?
- Fix missing handlers/fields inline; file larger fidelity work as P14-ISS-* or backlog (BL-549–552).

**4c. Cleanliness audit (find-and-flag):**
- Look for duplicate event emissions (pattern from P13-ISS-008 double `lifecycle_end`).
- Check for events written to wrong session/delegation.
- Check for best-effort writes that silently swallow errors (checkpoint save that fails but delegation succeeds).
- Check for contextvar leaks across delegations in the same process.
- Check for proxy routing catch-alls that misattribute (pattern from P9 `google/*` → OpenRouter).
- **Find-and-flag:** file as P14-ISS-* rather than fixing inline, unless the fix is one line. Keeps this bounded.

**Acceptance:**
- Full event-type → handler mapping documented (which types exist, which have handlers, which fields are surfaced).
- Capture completeness verified for at least one full-role delegation.
- Findings fixed (trivial) or filed (P14-ISS-*).
- No known silently dropped event types after this pass.

**Depends on:** P14-001 + P14-002 (new Supervisor events to verify). Can run initial audit in parallel with earlier tasks.

## Phase 15 connection

Phase 14 output feeds directly into the **Phase 15 MVP usage decision**:

- If the Supervisor can intercept easy `confirm_ask` and the logging shows its reasoning → **adopt MVP usage** on an external project.
- If interception is still mostly escalating and logs are opaque → **pause MVP usage**, keep developing.
- The pain log from Phase 15 dogfood feeds back into Phase 14-style improvements.

**Phase 14 is the last dev phase before the adopt/pause fork.** Phase 15 is validation, not development.
