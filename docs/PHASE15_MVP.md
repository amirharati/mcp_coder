# Phase 15 — Minimal viable intelligence (supervisor + planner + executor prompts)

**Status:** **Active** — opened 2026-06-25.
**Purpose:** Give the supervisor and planner a trace of real intelligence before MVP dogfood on an external project. The supervisor must reason about what the executor actually did (not pattern-match), and the planner must be able to look before it plans (not one-shot). The executor prompt should carry the plan and project state explicitly. Infra-first: reuse existing tools and functions; do not build new ones.
**PM board:** this file · **Issues:** [PHASE15_ISSUES.md](./PHASE15_ISSUES.md)
**Phase 14 (closed):** [PHASE14_MVP.md](./PHASE14_MVP.md) · [PHASE14_ISSUES.md](./PHASE14_ISSUES.md)
**Design notes:** [notes/supervisor-agent-architecture.md](./notes/supervisor-agent-architecture.md) · [notes/system-design-overview.md](./notes/system-design-overview.md)
**Backlog inputs:** BL-525 (planner as agent), BL-529 (supervisor context, partial), BL-543 (context lifecycle, partial), BL-547 (interception v1 shipped P14-002)

## One-line goal

Make the supervisor reason (not pattern-match), make the planner investigate (not one-shot), and make the executor prompt carry the plan — all by wiring existing infrastructure, not building new tools.

## North-star acceptance

After Phase 15:

1. **Supervisor reasons every delegation** — `_llm_decide` is the default path (not `_policy_decide`); the supervisor sees the diff and the builder brief before deciding done/rerun/escalate. Trace shows the enriched prompt in `llm_call(role=supervisor)`.
2. **Planner investigates before planning** — the planner uses a bounded tool-calling loop (`SupervisorToolRunner` with `read_file` + `get_project_state` + `get_delegation_history`) instead of one-shot. Trace shows planner tool calls.
3. **Prompt management layer in place** — `core/context/role_rules.py` with `build_role_rules(role)` is the single source of truth for shared + role-specific rules. Every helper LLM call sends a system message (rules) + user message (task context), not a single concatenated user message. The executor `system_prompt_prefix` carries shared + executor rules. The seam for future dynamic skills (topic-based, project-state-driven) exists without being populated.
4. **No new tools built** — all capabilities come from wiring existing functions (`build_delegation_diff`, `SupervisorToolRunner`, registered tools). If a worker finds itself writing a new tool function, stop and file an issue.

## Strategic context

Phase 14 closed the trust gap: the supervisor has context, the control loop intercepts, helper LLMs are audited, and logging is deep and clean. But the supervisor is still "dumb" in two concrete ways:

- **Inter-turn decision** (`SupervisorAgent._decide`): defaults to `_policy_decide` when `max_turns==1` (almost always), which is pure pattern-matching: `success→done`, `reviewer issues→rerun`, `else→done`. The LLM path (`_llm_decide`) exists and is more capable but only fires when `max_turns>1`.
- **Blind to the diff**: even when `_llm_decide` fires, the decision prompt has file *names* and stdout *tail* but not the actual diff. The supervisor can't reason about "the executor said success but the diff is empty."

Meanwhile the planner is strictly one-shot (`run_owned_helper_completion` → plan → done). No file reads, no project state lookup, no iteration.

The good news from the Phase 15 infra audit: `SupervisorToolRunner` already has `read_file`, `get_project_state`, `get_delegation_history`, and `get_reviewer_findings` registered (`core/engine/supervisor_tool_runner.py::build_phase12_tool_runner`). `build_delegation_diff` already exists (`core/workspace/history_query.py`). The work is wiring, not building.

**Phase 15 is NOT:**
- Full autonomous interception policy (BL-547 full vision)
- RAG-fed supervisor context (BL-557 sharing layer)
- CTO/Architect role (BL-526)
- Executor session adaptation (BL-546)
- Product UI
- Full multi-step investigation chains

Those stay in backlog. Phase 15 is the minimal slice that makes the system feel "not totally dumb."

## Milestones

### P15-000 — Prompt management layer + executor prompt enrichment

**Status:** `pending`
**Goal:** Build the prompt fragment layer (shared rules + role rules as a named, separable fragment) and use it to enrich the executor prompt. This is the lowest-hanging fruit: every helper LLM call benefits from consistent output rules, and the executor gets the plan + behavioral guidance + project state explicitly. The fragment layer is the seam where future dynamic skills enter without touching call sites.

**Strategic framing:** Every LLM call is an assembly of prompt fragments:

```
system message = role_definition + shared_rules + role_rules + [future: skills]
user message   = task_context
```

Today, all five fragments are mixed into a single user message per helper (preamble + context concatenated). P15-000 separates them so:
1. Shared rules are not duplicated across 6 preambles.
2. Rules live in the system message (where models weight them as instructions, not content).
3. `build_role_rules(role)` is the seam for future dynamic skills (topic-based, project-state-driven, RAG-retrieved) — call sites don't change when skills arrive.

For the executor (Aider), the same assembly happens at `model.system_prompt_prefix` (Aider prepends this to its `main_system`). Aider's own system prompt stays intact.

**Scope:**

| Slice | What | Where |
|-------|------|-------|
| **A. Create prompt fragment layer** | New `core/context/role_rules.py` with `build_role_rules(role) -> str` returning shared base rules (output format, no code fences, markdown only, be concise) + role-specific rules. Single source of truth — today these are duplicated across 6 preamble constants. | `core/context/role_rules.py` (new) |
| **B. Split + enrich helper preambles into system + user** | Two-part work: (1) **Structural split** — each helper (`planner_prompt.py`, `reviewer_prompt.py`, `clarity_prompt.py`, `spec_validation_prompt.py`, `builder_prompt.py`) moves rules to a system message and keeps only task context (spec, diff, brief, files) in the user message. Wire `run_owned_helper_completion` to accept a `system_prompt` param and emit `[{system}, {user}]` messages. Move `_SUPERVISOR_PREAMBLE` and `_DECISION_PREAMBLE` into system prompts too (supervisor confirm_ask currently passes `system_prompt=""`). (2) **Content enrichment** — review and strengthen each helper's role-specific rules using findings from the Phase 14 prompt audit. Known weak spots: planner prompt doesn't tell the model to check file feasibility before planning; reviewer is framed "junior" and can't check spec compliance; builder prompt is good but verbose; clarity is well-designed but could surface project state. The enrichment is per-role rules only — shared base rules come from Slice A. | All `core/context/*_prompt.py` + `core/engine/owned_helper_llm.py` + `core/engine/supervisor.py` + `core/engine/supervisor_agent.py` |
| **C. Enrich executor prompt** | Three changes: (1) `EXECUTOR_PULL_HINT_BLOCK` becomes `build_role_rules("executor")` + pull hint — injected via `model.system_prompt_prefix` (Aider prepends to its `main_system`). (2) Add `## Planner plan` as a distinct section in the executor user prompt (currently folded into builder brief). (3) Inject compact `## Project state` summary into executor user prompt via `ProjectState.to_summary()` (already exists from P14-001). | `core/engine/aider_engine.py` + `core/context/summary.py` |

**Not solved:**
- Dynamic skill injection (topic-based, project-state-driven, RAG-retrieved) — seam in place, not populated. Future: `build_role_rules(role, *, project_state=None, topic=None)`.
- RAG-fed executor context (BL-354 full)
- Executor-pull sidecar
- Per-delegation rule customization

**Acceptance:**
- `core/context/role_rules.py` exists with `build_role_rules(role)` returning shared + role-specific rules for every role (planner, reviewer, clarity, spec_validation, builder, supervisor_confirm, supervisor_decision, executor).
- Every helper LLM call sends a system message (rules) + user message (task context) — not a single concatenated user message. Trace shows the split in `llm_call` records.
- `run_owned_helper_completion` accepts a `system_prompt` param.
- Each helper's role-specific rules are reviewed and enriched per the Phase 14 prompt audit findings (planner: check feasibility; reviewer: spec compliance lens; etc.). No helper keeps a verbatim copy of its old preamble — all rules route through `build_role_rules(role)`.
- Executor `system_prompt_prefix` contains shared rules + executor rules + pull hint (not just the pull hint).
- Executor user prompt contains a distinct `## Planner plan` section when a plan exists.
- Executor user prompt contains a compact `## Project state` section when project state exists.
- Trace shows the enriched executor prompt in `prompt_full` / `STAGE_FINAL_EXECUTOR_PROMPT` compile event.
- No regressions in existing helper/executor tests.
- No new tools built.

**Depends on:** nothing (entry point). **Feeds:** P15-001 (cleaner executor output + consistent system prompts make supervisor reasoning more reliable).

### P15-001 — Supervisor intelligence v1

**Status:** `pending`
**Goal:** Make the supervisor reason about every delegation outcome instead of pattern-matching. Give it the diff and the builder brief so it can judge "did the executor actually do the work?"

**Scope:**

| Slice | What | Where |
|-------|------|-------|
| **A. Make `_llm_decide` the default** | Remove the `max_turns==1 → _policy_decide` shortcut in `SupervisorAgent._decide()`. The LLM path already exists and falls back to `_policy_decide` on any failure, so this is low-risk. Every delegation now gets a reasoning decision. | `core/engine/supervisor_agent.py::_decide` |
| **B. Inject diff into decision prompt** | `_build_decision_prompt` today has file *names* + output *tail* but not the diff. Reuse `build_delegation_diff(workspace, delegation_id)` (already exists) to inject a bounded diff (2-3k chars) into the prompt. | `core/engine/supervisor_agent.py::_build_decision_prompt` |
| **C. Inject builder brief into decision prompt** | The supervisor gets `self._plan` (1.2k truncated) but not the *builder brief* — the actual prompt the executor received. Pass the builder brief (or a summary) so the supervisor can check "did the executor follow the brief?" | `core/engine/supervisor_agent.py::_build_decision_prompt` + caller (server wires `context_package.brief`) |

**Not solved:**
- Richer interception policy (learning from past decisions)
- RAG-fed supervisor context (BL-557)
- Supervisor's own long-context policy (explicit future design area)
- Confirm_ask path getting the diff (Gap 5 from prompt audit — mid-execution diff capture is hard; defer to backlog)

**Acceptance:**
- `_llm_decide` fires for every delegation (not just `max_turns>1`). Trace shows `llm_call(role=supervisor)` with the enriched prompt for every turn.
- Decision prompt contains `## Unified diff` section (bounded) when a diff exists.
- Decision prompt contains `## Builder brief` section (bounded) when a builder brief exists.
- Supervisor can reason: "reviewer said LGTM but diff is empty — rerun" or "executor failed but diff looks correct — done."
- `_policy_decide` remains as fallback on LLM failure (no regression).
- No new tools built — `build_delegation_diff` is reused.

**Depends on:** P15-000 (cleaner executor output). **Feeds:** P15-002 (planner loop benefits from supervisor intelligence feedback).

### P15-002 — Planner agentic loop v1

**Status:** `pending`
**Goal:** Move the planner from one-shot to a bounded tool-calling loop. The planner can read files, check project state, and look at delegation history before producing a plan.

**Scope:**

| Slice | What | Where |
|-------|------|-------|
| **A. Planner uses `SupervisorToolRunner`** | Replace `run_owned_helper_completion` (one-shot) in `planner_pass_llm.py` with a `SupervisorToolRunner` call. Register the same tools the supervisor already has: `read_file`, `get_project_state`, `get_delegation_history`. Bounded to 3 iterations. | `core/engine/planner_pass_llm.py` + `core/engine/supervisor_tool_runner.py` (possibly a sibling `build_planner_tool_runner` or reuse as-is) |
| **B. Mutable plan** | The planner can revise its plan mid-loop (e.g., reads a file, discovers it's bigger than expected, splits the work). The final plan is what goes to the executor. | `core/engine/planner_pass_llm.py` (prompt + finalization) |
| **C. Trace capture** | Planner tool calls surface as `compile_event` entries with `stage=planner_tool_call` (or fold into existing `compile_event` with a new stage constant) so the viewer shows the planner's investigation. | `core/observability/trace.py` + `core/engine/planner_pass_llm.py` |

**Not solved:**
- RAG-aware planner (BL-525 full — `rag_search` as a planner tool; defer)
- Cross-delegation planner memory beyond existing project state
- Architect/CTO role (BL-526)
- Full mutable planning behavior (BL-525 full)

**Acceptance:**
- Planner makes tool calls (visible in trace) before producing a plan.
- Planner can revise its plan based on tool results (e.g., read_file reveals something unexpected).
- Trace shows `planner_tool_call` events (or equivalent `compile_event` with stage).
- Final plan still starts with `## Planner plan` and follows the existing format (no executor-side regression).
- Bounded to 3 tool rounds; falls back to one-shot on any failure.
- No new tools built — reuses `read_file`, `get_project_state`, `get_delegation_history`.

**Depends on:** P15-001 (supervisor intelligence provides feedback signal). **Feeds:** Phase 15 dogfood (planner quality directly affects executor quality).
